## 1. Primary dataset — NASA C-MAPSS Turbofan Engine Degradation Simulation

- **Source:** NASA Prognostics Center of Excellence (PCoE), Ames Research Center.
- **What it is:** simulated run-to-failure trajectories for a fleet of turbofan jet
  engines, generated by NASA's high-fidelity CMAPSS thermodynamic simulation model.
  This is the standard academic/industry benchmark dataset for Remaining Useful Life
  (RUL) prediction research — it is real, peer-reviewed, and publicly documented
  (not something we generated ourselves).
- **Subsets:**

| Subset | Operating conditions | Fault modes | Difficulty |
|---|---|---|---|
| FD001 | 1 | 1 (HPC degradation) | Easiest — **start here** |
| FD002 | 6 | 1 | Harder |
| FD003 | 1 | 2 (HPC + fan) | Harder |
| FD004 | 6 | 2 | Hardest |

**Use FD001 for the Day 1 working prototype.** Only attempt FD002/FD004 if time
allows — they are meaningfully harder and not necessary to prove the concept.

- **Columns (per row = one engine, one cycle):**
  `engine_id, cycle, op_setting_1, op_setting_2, op_setting_3, sensor_1 ... sensor_21`
- **Train files:** full run-to-failure trajectories (used to compute RUL labels).
- **Test files:** trajectories truncated before failure — the true RUL for each test
  engine is provided in a separate `RUL_*.txt` file. **Always evaluate against this
  official test split**, not an arbitrary random split (see `docs/ML.md` Section 3).

### How to download (you must do this locally — not available inside this environment)

1. Go to the NASA Prognostics Data Repository / PCoE page for Turbofan Engine
   Degradation Simulation Data, or the mirrored download on the PHM Society /
   IEEE DataPort (search "NASA C-MAPSS turbofan engine degradation dataset").
2. Download the zip for the Turbofan Engine Degradation Simulation Data Set.
3. Extract into `ml/data/CMAPSS/` so the structure is:
   ```
   ml/data/CMAPSS/
   ├── train_FD001.txt
   ├── test_FD001.txt
   ├── RUL_FD001.txt
   └── ... (FD002–FD004 similarly, if used)
   ```
4. `ml/data/` is gitignored (large data files should not be committed) — only
   `ml/data/README.md` (a pointer, not the data itself) is tracked in git.

## 2. Synthetic data — spares & maintenance logs (illustrative only)

Because we have no real integrated spares/maintenance-records system to pull from,
`backend/app/models/spares.py` generates a small, clearly-labelled **synthetic**
table that represents what this data *would* look like, so we can demonstrate the
data-fusion integration pattern the PS explicitly asks for.

**Schema (illustrative):**

| Field | Type | Example |
|---|---|---|
| `part_id` | string | `"ENG-BEARING-04"` |
| `part_name` | string | `"High-pressure compressor bearing"` |
| `compatible_engine_ids` | list[string] | `["engine_12", "engine_47"]` |
| `stock_quantity` | int | `3` |
| `lead_time_days` | int | `7` |

**Rule (restated from `PROJECT_BRAIN.md`):** any UI or doc referencing this table
must visibly label it as illustrative/synthetic data, standing in for a real
spares-management system integration.
